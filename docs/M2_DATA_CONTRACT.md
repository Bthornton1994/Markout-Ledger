The engine (Milestone 1) replays a JSONL fixture in which every observation carries `obsTime` (when the strategy could first know it) and `marketTime` (when it happened at the venue), consumes it lazily in file order, and rejects what it cannot trust (EVENT_SCHEMA.md). Two artifacts, one direction:

```
venue feed --(capture, first party)--> raw capture v1 (immutable) --(normalize)--> replay fixture v2 --(replay)--> ledger
```

## 1. `obsTime`: definition and prohibitions

`obsTime` is the **local wall-clock time, in integer milliseconds since the Unix epoch, at which the capture process finished receiving the raw frame that carries the observation**, taken by the capture process from the operating system's realtime clock at receipt and before any parsing.

Rules:

1. `obsTime` is never derived from any venue field: not the event time, not the trade time, not a block timestamp, not a checksum or sequence number, and not "venue time plus a typical latency".
2. Data without a receive timestamp recorded by an identified capture process (venue historical archives, exchange CSV dumps, database extracts) is **venue-time-only data**. It is never labelled `synthetic: false` with a replay time basis. The normalizer cannot prove that a receive clock is genuine; what it can do is refuse anything that does not come from a raw capture v1 file written by an identified capture tool (R1) and apply the plausibility checks of R1b. Converting an archive into raw capture v1 by inventing receive clocks is a violation of this contract, not a workaround.
3. The capture process records two clocks per record: `recvWallMs`, the realtime clock in integer milliseconds (`Date.now()` in Node, read independently of any monotonic source), and `recvMonoNs`, the monotonic clock in nanoseconds (`process.hrtime.bigint()`). `recvWallMs` becomes `obsTime`. Deriving the wall clock from the monotonic one (start time plus elapsed) is forbidden: the two must be able to disagree, because their disagreement is how clock steps are detected (§5.6).
4. The capture host runs a disciplined clock (NTP or PTP, e.g. `chronyd`). The manifest records the synchronization report at start and end (§4.2). `clockSync` is `synchronized` only if both reports show a synchronized state with `|offsetMs| <= 5`; otherwise `unknown`, and the evaluation protocol classifies the session's results as inconclusive (I6). The capture also probes the venue clock (§8.1) and the normalizer records the estimated host-to-venue offset and the probe resolution (§5.6); a host clock that runs behind the venue makes orders look live earlier than they were, so the bound is enforced where the probe resolution allows it and reported where it does not.
5. Third-party receive timestamps (a data vendor's own capture time) are a distinct time basis, `third_party_receive`. They are not "actual local receive time" and their latency distribution is not ours. The M2 build does **not** implement this basis: `validateHeader` rejects it with "time basis not implemented". When a later milestone adds it, the header must name the vendor, the capture location and the licence (schema: `provenance.capture.vendor` becomes required), the CLI banner and results must print the basis, and the evaluation protocol must report it separately.

`marketTime` is the venue's own timestamp for the event, in integer milliseconds, from the field the adapter names (§8.5). The selected venue stamps books and trades in RFC 3339 with microseconds; `marketTime` is that instant floored to the millisecond, and the full string is kept in `venueSeq`.

## 2. Capture path (first party, market data only)

No legitimately usable recorded session with receive timestamps exists for the selected venue (M2_DATA_SOURCE_DECISION.md §2, §3), so the session is produced by our own capture, from the host confirmed under decision condition C3, operated by the person confirmed under C3, in a US state the venue serves (M2_DATA_SOURCE_DECISION.md §1, conditions):

- A capture process connects to the venue's **public** market-data endpoints only. No API key, wallet, account or order path exists in the capture code; the package must not contain order-placement code at all. This is a review criterion.
- It subscribes to the book channel (with the venue's in-band snapshot), the trade channel and the instrument channel of exactly one instrument (§8.1), and appends every received frame **verbatim** to the raw capture with both receive clocks, in arrival order. It never reorders, dedups, parses-and-drops, or rewrites.
- It records its own lifecycle (connect, disconnect, reconnect, every request it sends, clock probes, errors) as records in the same stream with receive clocks, so a normalizer can prove what was known when.
- It maintains the same local book as the normalizer, through one shared adapter module, and performs the same live checks: the per-message checksum of §8.2, a crossed local book and a malformed depth update (§5.3). On any of them it resubscribes (the `unsubscribe` echoing the subscribed depth, then `subscribe`), so that a fresh snapshot follows every cut the normalizer will make for those reasons; without that, the remainder of a capture after such a cut would be unusable. Clock steps (§5.6) need no resubscribe because the normalizer carries the book over. The live checks never change what is written: the frame that revealed the condition is appended verbatim like any other, and the cut itself is the normalizer's. They do run on the same thread as the receive stamps, so work done on frame N can delay the stamp of frame N+1 by the handler's duration; the capture therefore takes both clocks as the first action of the frame handler, keeps the handler's work minimal, and writes the handler-duration percentiles (`processingMs: {p50, p99, max}`) into `manifest_end` so the delay is auditable. Resynchronizations and reconnections each have a budget of 5 in any sliding 300 s on the monotonic clock, a resync counted when its `unsubscribe` is sent and a reconnection when any socket after the first starts opening. A failed resync (its `unsubscribe` or `subscribe` answered with `success: false`, or no `snapshot` before its 10 s timer, started at the `unsubscribe`, fires) closes the socket and escalates to a reconnection, which counts toward the reconnection budget. A sixth of either kind within 300 s is never started: the capture ends with `ws_error` naming the exhausted budget instead. §8.1 defines the counting, the boundary and the timeouts exactly.
- Liveness: the venue sends a heartbeat about once per second when nothing else is flowing [S] (§8.1). If no frame of any kind arrives on an open socket for 15 s, counted from its opening or from its last frame, the capture closes it (`ws_close`, detail `liveness_timeout`) and reconnects, subject to the reconnection budget; a socket that has not opened 10 s after the runner started opening it, has not had each of its three subscriptions acknowledged 10 s after sending it, or has delivered no book snapshot or no instrument snapshot 10 s after the corresponding `subscribe` was sent, is a failed attempt too (§8.1); every reconnect is a segment boundary.
- It runs for a target duration (default 90 minutes), measured on the monotonic clock from `manifest_start`, and rotates raw files at most hourly; every file is closed with its SHA-256. At the planned end, and when the operator stops it (SIGINT or SIGTERM), it settles the socket with `ws_close` detail `capture_end` or `operator_stop` (`ws_error` with the same detail for an attempt still connecting), then writes `file_end` and `manifest_end` (§8.1). Every end the lifecycle table of §8.1 names (the planned end, an operator stop, `subscribe_rejected` and an exhausted budget) writes `file_end` and `manifest_end`; a capture that stops without them (a crash, a kill, a power loss) has no `manifest_end`, and the normalizer refuses it (R1).

A **usable session** is a capture segment that the normalizer accepts under §5 end to end: a checksum-verified top of book on every applied update (the checksum covers the top 10 levels per side; deeper emitted levels derive from the same verified stream but are not covered, §5.3), ended by an admissible reason (M2_EVALUATION_PROTOCOL.md §3), a negative-lag share within R2's bound, a bounded venue clock offset where measurable, at least 60 minutes (evaluation) or 10 controller windows (acceptance tests), with the sync report present. The first usable session is the acceptance input for the M2 build.

## 3. Immutability and provenance chain

| artifact | identity | hash |
|---|---|---|
| raw capture file | `captureId` (a lower-case UUID version 4 chosen at start; all three schemas require that form) + `fileIndex` | SHA-256 over every byte of the file that precedes its `file_end` record, written into `file_end.sha256` and repeated in `manifest_end.files` |
| capture manifest | `captureId` | `manifest_start` is the first record of file 0; `manifest_end` is the last record of the last file, **after** that file's `file_end`, and is excluded from every hash |
| replay fixture | `provenance.capture.captureId` + `segmentIndex` | `fixtureContentHash` (existing canonical hash over header and events) |
| ledger | `replay_started.fixture.contentHash` and `replay_started.fixture.provenance` (which, in v2, carries `capture`, `instrumentSpec` and `rights`, §6.1) | existing hash chain |

Raw files are never modified after close. The normalizer recomputes every file hash before doing anything else (R1b). A normalizer re-run must reproduce a byte-identical fixture from the same raw files and the same normalizer version (acceptance test A1); the fixture header records the capturer and normalizer identities with their commits and the adapter's name and version (the adapter ships inside the normalizer, so its commit is the normalizer's).

Trust model, stated plainly: the contract makes receive times *auditable* (immutable raw files, identified capture tool and host, clock reports, plausibility checks), not *provable*. The `capturer.commit` names the code that wrote the clocks; anyone re-running that code on their own host can compare lag distributions.

## 4. Raw capture format v1

One uncompressed JSONL file per rotation, named `<captureId>-<fileIndex>.jsonl`, records in arrival order. Record index = 0-based line number within its file, counting every record type. Every record has `type`, `recvWallMs` (integer), `recvMonoNs` (string, integer nanoseconds). The runner reads both clocks afresh for every record, at the moment it writes it: a `message` record carries the clocks its frame handler took first (§2), a request record its send clocks, and every record the runner writes on its own (a lifecycle, note, file or manifest record, including one a tie makes the frame handler write, §8.1) clocks read when that record is written, never a timer's deadline and never another record's clocks. If a reading of the monotonic clock does not exceed the previous record's `recvMonoNs`, the runner reads again until it does, so the file is strictly increasing (R1b) and no value is adjusted; an injected test monotonic clock therefore advances by at least 1 ns on every reading, and an injected test wall clock moves with it, so the test double creates no clock step (§5.6) unless a test injects one. Payloads are the exact text received (`payload` is a string; binary frames are base64 with `encoding: "base64"`). Valid examples of every record type are in `schemas/examples/capture-record.v1.examples.json` (values constructed by the authors, not venue data); `tests/schemas.test.ts` validates them, and failure cases derived from them, against `schemas/capture-record.v1.schema.json` in CI (`npm run test:schemas`).

### 4.1 Records

| `type` | additional fields | meaning |
|---|---|---|
| `manifest_start` | `captureFormatVersion: 1`, `captureId`, `venue`, `instrument` (venue-native symbol), `streams` (the subscription requests, verbatim), `endpoints` (`ws`, `rest`), `capturer` (`name`, `version`, `commit`), `host` (`os`, `runtime`; no hostnames or addresses), `clock` (§4.2), `instrumentSpec` (`source`, `fetchedAtIso`, `payload`: the verbatim REST instrument response, §8.4), `startedAtIso` | first record of file 0 |
| `file_start` | `fileIndex`, `previousFileSha256` | first record of every file after file 0 |
| `ws_open` / `ws_close` / `ws_error` | `detail`: only the values of the lifecycle table of §8.1, which the schema enforces | connection lifecycle; every socket the runner starts opening after the capture's first is a reconnection (§8.1), whether it opens or ends in `ws_error` detail `connect_failed` or `connect_timeout` |
| `subscribe` / `unsubscribe` / `ping` | `request` (verbatim text sent) | written at send time (the record's clocks are the send clocks); its `req_id` exceeds every earlier request's `req_id` in the capture (§8.1, Request identity); the venue's response arrives as an ordinary `message` record and is matched by `req_id` to a request of the same socket |
| `message` | `stream` (the frame's `channel`, or `method:<name>` for method responses, or `unknown`), `payload` | one received frame |
| `probe` | `url`, `sentWallMs`, `sentMonoNs`, `payload` | REST venue clock probe (coarse: sent at capture start, before the runner starts opening its first socket, then every 10 minutes, §5.6): request send clocks plus the verbatim response; the record's own clocks are the response receive time |
| `note` | `detail` (free text) | operator or tool note (clock step detected, checksum mismatch, crossed book, malformed update, resubscribe issued; no checksum, crossed-book, malformed-update or resubscribe note while a resync is outstanding, §8.1); timeouts, failed attempts, closes, planned ends and exhausted budgets are recorded in the `detail` of `ws_close` and `ws_error` (§8.1) |
| `file_end` | `fileIndex`, `records`, `sha256` | last hashed record of a file: `sha256` covers all bytes before this record; `records` counts records before it |
| `manifest_end` | `endedAtIso`, `clock` (§4.2), `counts` (records by type), `files` (`fileIndex`, `sha256`, `records`), `processingMs` (required: `p50`, `p99`, `max` frame-handler durations in milliseconds over every received frame, §2; all three are 0 when no frame was received) | follows the last file's `file_end`; excluded from every hash |

### 4.2 `clock` block

```json
{"source": "chrony", "report": "<verbatim `chronyc tracking` output>", "offsetMs": -0.31, "stratum": 2, "synchronized": true, "takenAtIso": "..."}
```

`source` is `chrony`, `ntpd`, `ptp`, `platform` (cloud-provided sync with its own report) or `unknown`. `synchronized` is false when the tool reports an unsynchronized state or no report could be taken. The verbatim `report` (which names NTP servers by address) stays in the raw manifest only; the fixture header's `clockReports` (§6.1) carry the parsed fields (`source`, `offsetMs`, `stratum`, `synchronized`, `takenAtIso`) and never the report text, so no address reaches a fixture, a ledger, `results.json` or a public PR (§4.1, `host` rule). The fixture schema closes `clockReports` and its `start` and `end` blocks to unknown keys (§6, unknown properties), so the report text cannot travel there under another key; keeping it out of the fixture's other, deliberately open objects is the normalizer's rule (it writes parsed fields only), not the schema's.

## 5. Normalization contract

The normalizer is a pure function of (raw files, adapter version, options). It emits zero or more **segments**; each segment becomes one fixture file. It never emits a fixture for a segment it could not fully verify.

### 5.1 Adapter interface

A venue adapter decodes verbatim payloads into typed messages and nothing else:

```
decode(record) -> { kind: 'snapshot', symbol, checksum, venueTimeText?, venueTime?, bids: [[price,size]...], asks: [[price,size]...] }
              |  { kind: 'depth',    symbol, checksum, venueTimeText,  venueTime,  bids, asks }
              |  { kind: 'trades', history: boolean, items: [{ symbol, tradeId, price, size, venueTimeText, venueTime, aggressor: 'buy'|'sell'|'unknown', offBook: boolean, ordType }] }
              |  { kind: 'instrument', type: 'snapshot'|'update', pairs: [{ symbol, text }] }      (each pair's verbatim JSON text)
              |  { kind: 'status', system }
              |  { kind: 'response', method, reqId, success?, channel?, symbol?, depth?, timeIn?, timeOut? } (method responses: acks, pong; channel, symbol and depth are the result fields the response echoes, when present)
              |  { kind: 'ignore', reason }                              (heartbeats, other channels)
              |  { kind: 'malformed', reason }
```

Prices, sizes and checksums are the **exact JSON lexemes** as received. The adapter parses with a lossless reviver (`JSON.parse(text, (key, value, context) => typeof value === 'number' ? context.source : value)`, which keeps every number's source text; Node 21 or later, verified on the Node 22 line used by this repository) and never passes a price or size through binary floating point. If the venue sends a price or size as a JSON string (the official fixtures carry JSON numbers [R], the official Rust SDK accepts a string or a number [R `kraken-api-sdk` `rust/src/book/wire.rs:21`], and what the venue's documentation says about the wire type has not been read [U], decision §4), the string's content is the lexeme and the same rules apply. Lexeme rules, because the venue's own SDK documents that a quantity "may be tiny, e.g. `5.1e-05` on the wire" (`kraken-api-sdk` `rust/src/api/market/ws_types.rs:108-119`, trade channel): for **trade** items and **instrument** fields an exponent lexeme is legitimate and is converted exactly to a plain decimal string (`5.1e-05` -> `0.000051`) before parsing; for **book** levels the checksum of §8.2 is computed from the lexeme as sent and no source read gives the venue's checksum string for an exponent lexeme [U], so a book price or size whose lexeme contains an exponent is `malformed` (the segment is cut, R6, counted as `dropped.exponentLexemeInBook`), and the first real capture reports the count (handoff A12) so the rule can be replaced by an evidenced one if the venue ever sends such a level. A sign or more than one leading zero in any lexeme is `malformed`. `venueTime` is the RFC 3339 field floored to integer milliseconds; `venueTimeText` is the field verbatim.

The adapter also declares the instrument specification from the instrument channel's snapshot (§8.4), cross-checked against the manifest's REST payload: `venueSymbol`, `tickSize` (the price increment), `lotSize` (the quantity increment), `priceDecimals`, `qtyDecimals`, `qtyMin`, `costMin`, `costDecimals`, `status`, `aggressorSource` (`maker_flag` / `taker_side` / `none`), `tradeStreamGranularity` (`per_fill` / `aggregated`), `tradeIdOrdered` (boolean), `integrity` (`crc32_top10` / `sequence` / `none`), `source`, `fetchedAtIso`. Increments are written as plain decimal strings; an exponent lexeme in the instrument data (`1e-08`) is converted exactly.

### 5.2 Ordering and identity

- Fixture order is raw arrival order; within one raw record that carries several items (a trade frame), array order. `seq` is assigned 1, 2, 3... in emission order within a segment.
- `eventId = ${captureId}:${fileIndex}:${recordIndex}:${elementIndex}` (`elementIndex` 0 for records that carry one observation, the array index for multi-item frames). `rawRef = {fileIndex, record, element}`. Every eventId in a segment is unique by construction, so the engine's `duplicate_event` rule cannot fire on a correctly normalized fixture (acceptance A9/A11 assert this).
- `event.symbol` and `header.symbol` are the venue-native symbol (`BTC/USD`; `header.venueSymbol` repeats it); `event.venue` and `header.venue` are the adapter's venue name (`kraken-spot`).
- `obsTime = recvWallMs` of the record that carried the observation. The normalizer **asserts** `obsTime` non-decreasing across the events of each segment (it may decrease from one segment to the next, across a backward clock step, R3). A failed assertion is a defect of the normalizer, not a condition of the data, so it has no rule code: the run stops, writes no fixture and no normalize report, and exits with an error naming the segment and the record (fail closed; it cannot happen if §5.6 is implemented, and the assertion is the proof).

### 5.3 Book synchronization and reconstruction

The normalizer maintains a full local book per segment from the venue's in-band snapshot plus its incremental updates, per the venue's documented procedure (adapter §8.2 instantiates it). Generic rules:

- **Snapshot.** The first `snapshot` after a `subscribe` replaces the local book. Its integrity value is verified (§8.2); a failed verification is a reconstruction failure (R6). The snapshot is **not** emitted as an event: a snapshot alone is not a verified stream position.
- **Update.** Each update is applied in full (a level with size zero removes the level; otherwise it replaces the level's size; a size-zero for a level the local book does not hold is a no-op counted as `dropped.deleteOfUnknownLevel`), each side is then truncated to the subscribed depth (the venue does not send removals for levels that fall out of scope [S], decision §2), and only then is the integrity value computed over the post-apply state and compared with the message's. A level whose price is not a multiple of `tickSize` or whose size is not a multiple of `lotSize`, or whose lexeme is malformed (§5.1), makes the whole message malformed (R6, `malformed_depth`): a book is never emitted with a level left out. A mismatch is a cut (`endReason: checksum_mismatch`, §5.8) at the raw record before the mismatching message; the mismatching message is not applied and nothing after it is applied until the next snapshot (`dropped.depthWhileUnsynced`).
- **First event.** The segment's first `book` event is the first verified update after its baseline: the snapshot, for a segment that starts at a snapshot, or the carried-over verified book, for a segment opened by a clock cut (§5.6). On each socket, no segment starts before the socket's subscription gate has passed. The gate passes at the later of two points: the first `success: true` acknowledgement that answers and matches each of the socket's initial `book`, `trade` and `instrument` subscriptions (§8.1, Request identity and Subscription identity), whichever of the three comes last, and the socket's first instrument snapshot, which must carry the selected pair with status `online` and the capture-start specification (§8.1, Instrument identity; R5, R9). A segment lies after its socket's gate record and before the first record of that socket's settlement (§5.8, one socket per segment). An update before the gate is still applied and verified as usual but emits nothing and is counted (`dropped.depthBeforeSubscribed`, or only `dropped.socketNotSubscribed` on a socket R9 refuses), and the segment's first event is the first verified update after the gate, so a segment never covers time in which a required channel was not yet subscribed. A baseline yields a segment through its first verified update after the gate, and otherwise as follows. A baseline received after the gate and never followed by a verified update before the next snapshot, the socket's terminal record or the end of capture is a refused segment with no event (R6, no verified update after the baseline): its `start` is the baseline, it uses the next segment index, and its `endReason` is given by the record that ends it under the precedence of §5.8 (`reconstruction_failure` at the next snapshot, `gap_disconnect` at a lifecycle record, `capture_end` at the planned end or an operator stop). A baseline received before the gate with no verified update after the gate before the next snapshot or the socket's terminal record yields no segment and uses no segment index, whether or not verified updates preceded the gate. A snapshot that fails its own checksum verification (§8.2 step 2) is no baseline and opens nothing: it and the book messages after it until the next snapshot are `dropped.depthWhileUnsynced`, and it yields no segment and uses no index. A socket that R9 refuses yields no segment of any kind (written, too short or refused) and uses no segment index (R9, §5.8).
- **Every verified update inside a segment (after the socket's subscription gate, First event above) emits one `book` event**, whether or not the top `depth` levels changed, so the policy's book age (`maxBookAgeMs`) reflects what the feed delivered. Its `obsTime` is the update's receive time and its `marketTime` the update's venue time. The event carries the top `depth` levels of the local book (`--depth`, default 25 for this venue, never more than the subscribed depth). The integrity value covers the top 10 levels per side (§8.2); levels 11 and deeper are derived from the same verified update stream but are not themselves checksummed, and the header says so (`instrumentSpec.integrity: crc32_top10`); `--depth 10` yields a fully checksummed fixture at the cost of visible span. Levels beyond the subscribed depth are unknown and never invented. The default of 25 keeps a 60-minute fixture within what the engine's loader can read (handoff S3 makes the loader streaming; until then a fixture must stay below 500 MiB).
- **Visible span.** Because the execution model seeds a level absent from the visible book with a queue of zero (EXECUTION_MODEL.md, `goLive`), the normalizer records per segment the distance in basis points from mid to the worst emitted level on each side (`visibleSpanBps.bid` / `.ask`, `p1` and `p50` over book events), computed per event in integer arithmetic on the engine's scaled prices as `floor(10000 * (mid - worstBid) / mid)` and `floor(10000 * (worstAsk - mid) / mid)` with `mid = (bestBid + bestAsk) / 2` (integer division), percentiles nearest-rank as in §5.6. The evaluation protocol uses it (I8).
- A crossed reconstructed book (best bid `>=` best ask) is a reconstruction failure (R6). The engine's own `crossed_book` rejection remains as a second line. The capture tool detects the same condition live on the same local book and resubscribes (§2, §8.1), so a fresh snapshot follows; the normalizer cuts here regardless of what the capture did.
- **Reset.** A `snapshot` that arrives while a segment is open (the venue re-sends one after a resubscribe or a reconnect) ends the segment (`endReason: snapshot_reset`) and starts a new one.
- No update is ever buffered and applied later: on this venue the snapshot arrives in band before any update of the subscription, so every applied update is emitted at its own receive time. An adapter for a venue that needs buffering must add its own rule here and bump the adapter version (§9).

### 5.4 Trades and aggressor side

Each trade item emits one `trade` event with `marketTime` = the venue's trade time, `tradeId` = the venue's trade id as a string, `aggressor` per the adapter. If the venue gives no aggressor information the value is `unknown` and `instrumentSpec.aggressorSource` is `none`; the engine treats `unknown` prints as able to fill either side, which is the more pessimistic picture. The selected venue names the taker side explicitly (§8.3).

A trade frame whose `type` is `snapshot` carries recent history, not new prints; it is never emitted and is counted (`dropped.tradeSnapshotHistory`). Items the adapter marks `offBook: true` (block trades, trades against hidden order types that never appear in the book) are **not emitted**: they did not consume visible-book liquidity and would let the engine award fills against a queue that never existed. They are counted (`dropped.tradeOffBook`). The selected venue's trade channel has no such flag; `offBook` is always false there.

Limitations recorded in the header: whether the trade stream is per-fill or aggregated (an aggregated stream can merge several fills of one taker order into one print; the M1 rule "a fill is never larger than the printed trade size" then bounds by the merged size), and which venue clock each stream carries (§5.6). A search excerpt of the selected venue's documentation says that one message may batch several trades and that batching does not imply one taker order [S] (§8.3); the adapter declares the stream `per_fill` (§8.4), an assumption that this excerpt does not establish (it concerns how trades are batched into messages, not whether one print is one fill) and that the owner's reading of the trade page confirms before capture (decision condition C5).

### 5.5 Price and quantity conversion (exactness, and the precision prerequisite)

The engine is fixed point on `bigint` (`src/core/money.ts`): `PRICE_SCALE`, `QTY_SCALE` and `MONEY_SCALE` are powers of ten, and `parseDecimal` **refuses** any decimal string with a non-zero digit beyond the scale's places. Nothing is rounded or truncated on the way in, ever.

Exactness condition. Every valid price of an instrument is an integer multiple of its price increment and has at most `priceDecimals` decimal places; it maps into the engine exactly if and only if `priceDecimals <= decimalsOf(PRICE_SCALE)`. Likewise every valid quantity maps exactly if and only if `qtyDecimals <= decimalsOf(QTY_SCALE)`. Notional (`price * qty`) is rounded half-up to `MONEY_SCALE` by the engine's documented accounting rule; the venue's `costDecimals` bounds nothing on our side.

Evidence for the selected instrument (Kraken `BTC/USD`, instrument-channel example in the venue's documentation; re-fetched verbatim at every capture and cross-checked, §8.4; source labels in M2_DATA_SOURCE_DECISION.md §5):

| quantity | venue value | engine scale today | exact today? | after handoff §0 (`QTY_SCALE = 1e-8`) |
|---|---|---|---|---|
| `price_precision` / `price_increment` | 1 / `0.1` | `PRICE_SCALE = 1e-6` (6 places) | yes (1 <= 6) | yes |
| `qty_precision` / `qty_increment` | 8 / `1e-08` | `QTY_SCALE = 1e-6` (6 places) | **no** (`0.00000001` is `0.01` units) | yes (8 <= 8) |
| `cost_precision` | 5 | `MONEY_SCALE = 1e-6` | not a constraint | not a constraint |

Consequences, all fail closed:

- R5 refuses to normalize any capture whose `instrumentSpec.priceDecimals` exceeds `decimalsOf(PRICE_SCALE)` or whose `qtyDecimals` exceeds `decimalsOf(QTY_SCALE)` of the engine that runs the normalizer. On the current engine this refuses `BTC/USD`. No rounding mode exists.
- The versioned migration `QTY_SCALE: 1e-6 -> 1e-8` is a **prerequisite** for this instrument, specified in M2_GROK_HANDOFF.md §0 as its own PR. It is not part of this documents-only PR and not part of the capture/normalize PR.
- Substituting an instrument that fits today (`qty_precision <= 6` and `price_precision <= 6`) would avoid the migration; no such Kraken instrument has been verified from the authoring environment (no instrument listing was reachable), and the evaluation objective (a liquid USD spot market) keeps `BTC/USD` provisionally selected. The choice between the migration and a substitute is made only after the handoff §0 P0 listing, which enumerates fitting pairs from a live instrument snapshot and runs only after decision conditions C2 and C3 are met.
- The cross-check of §8.4 (REST `pair_decimals`, `lot_decimals`, `tick_size` against the instrument channel's `price_precision`, `qty_precision`, `price_increment`) must agree; a disagreement is R5. So must every later instrument frame, on every socket, that carries the pair: a frame that gives it another `price_precision`, `qty_precision`, `price_increment` or `qty_increment` than the capture-start specification (increments compared by value, so `1e-08` equals `0.00000001`) is R5 (§8.4).

Malformed items (R4): an undecodable frame on any stream other than the book channel is `dropped.undecodable`, counted once per frame and on any socket (its channel cannot be known). Every item of a decodable trade frame is counted under at most one `dropped` key, the first that applies in this order: `dropped.socketNotSubscribed` (the frame is on a socket that R9 refuses, §5.9); `dropped.tradeSnapshotHistory` (the frame's `type` is `snapshot`, §5.4); then, per item, `dropped.foreignSymbol` (its `symbol` is not the selected instrument's), `dropped.nonPositiveTradeSize`, `dropped.offTickPrice` (its price is not a multiple of `tickSize`), `dropped.offLotSize` (its size is not a multiple of `lotSize`), `dropped.tradeWhileUnsynced` (§5.8), `dropped.tradeOffBook` (§5.4), `dropped.tradeDuplicate` and `dropped.tradeIdRegression` (§5.7). The R4 items are those counted under `undecodable`, `foreignSymbol`, `nonPositiveTradeSize`, `offTickPrice` and `offLotSize`; none is emitted, and a trade of another pair is never emitted as the selected instrument's. Anything wrong inside a **book** message (undecodable payload, malformed lexeme, off-tick or off-lot level, missing checksum or timestamp, foreign symbol) cuts the segment (R6, `malformed_depth`) because the book can no longer be trusted; nothing on the book stream is ever silently dropped. Header and event decimals are written through `fmtPrice`/`fmtQty` at the engine's scales; `instrumentSpec` keeps the venue's values as plain decimal strings.

### 5.6 Clock basis, skew and steps

- Venue time and receive time are on different clocks. The lag `obsTime - marketTime` is network latency plus the venue's publication delay plus the host-to-venue clock offset. The normalizer computes, per segment and per stream (`book`, `trade`), `lagStatsMs = {count, min, p1, p50, p99, max}` and writes it into the header. Percentiles everywhere in this contract are nearest-rank on the sorted integer values (`p_q` is the `ceil(q * count)`-th smallest, 1-based; `p1` uses `q = 0.01`), so two normalizers agree bit for bit.
- **Venue clock offset, millisecond probes (WebSocket method responses).** The venue's method responses carry `time_in` (request received on the wire) and `time_out` (response sent on the wire), RFC 3339 with microseconds; a documentation excerpt shows this for subscription acknowledgements [S] and modelled in the venue's official CLI for order methods, while for `pong` the documentation excerpt shows the fields and the official CLI models none (M2_DATA_SOURCE_DECISION.md §2, row "venue timestamps"), so the build assumes them on **no** response and uses every response that carries them. A response is a usable sample only when both `time_in` and `time_out` are RFC 3339 date-times (`YYYY-MM-DDTHH:MM:SS`, an optional fraction of up to nine digits, of which those beyond the microsecond are dropped, and `Z` or an offset); any other value makes it no sample. Every request the capture sends (`subscribe`, `unsubscribe`, `ping`, §4.1) is a candidate probe: with `t0 = ` the request record's `recvWallMs` (its send clock), `t1 = time_in`, `t2 = time_out`, `t3 = ` the response record's `recvWallMs`, the response matched by `req_id` to a request of the same socket (§8.1, Request identity), the offset sample is `((t1 - t0) + (t2 - t3)) / 2` and the round trip `(t3 - t0) - (t2 - t1)`. All four instants are integer microseconds (`t0`, `t3` from the millisecond clocks times 1000; `t1`, `t2` from the RFC 3339 strings), the sample is the integer division of the sum by 2, truncating toward zero, medians are nearest-rank (the `ceil(count / 2)`-th smallest), and the header values are the integer microseconds divided by 1000 written with exactly three decimals (`1.234`). The capture sends a `ping` every 30 s on the open socket (§8.1, Every socket). When a segment owns at least 3 such samples (sample ownership, below) the normalizer records `venueClockOffsetMs = {samples, medianMs, medianRttMs, maxAbsMs, resolutionMs: 1, source: "ws_method_response"}` and R2b refuses the segment if `|medianMs| > 50` or `medianRttMs > 500`. The sign matters: a host clock behind the venue makes our orders appear live earlier on the venue clock than they were (optimistic eligibility); the evaluation protocol treats `|medianMs| > 25` as inconclusive (I6).
- **Coarse probe (REST, always on).** The capture also issues `GET /0/public/Time` as `probe` records: once when it starts, sent before it starts opening its first socket, and then every 10 minutes. That endpoint returns whole seconds (`unixtime`), so its estimate has `resolutionMs: 1000`. A probe is a usable sample only when its payload parses as JSON whose `error` is an empty array and whose `result.unixtime` is an integer; any other probe is no sample. Its instants, in integer microseconds, are `t0 = sentWallMs * 1000`, `t3 = ` the probe record's `recvWallMs * 1000`, and `t1 = t2 = unixtime * 1000000 + 500000` (the middle of the second the venue reported, whose true instant lies anywhere in it); the offset sample and the round trip then follow the formulas above (the round trip is `t3 - t0`), with the same division, nearest-rank medians, `maxAbsMs` the largest absolute offset and the same three-decimal format. When a segment owns fewer than 3 millisecond samples and at least one usable probe, the header records that coarse estimate from the probes it owns, `samples` counting those probes, with `source: "rest_time"`, and R2b only refuses gross errors (`|medianMs| > 2000` or `medianRttMs > 1000`); the segment can be written and replayed, but the protocol's I6 fails every evaluation cell built on it, because no bound comparable to 25 ms can be established at one-second resolution (M2_EVALUATION_PROTOCOL.md §4, I6). A segment that owns neither kind of sample records `samples: 0`, `source: "none"` and is refused (R2b).
- **Sample ownership.** A segment owns exactly these samples, all recorded by the capture as it runs and chosen by the normalizer from the raw stream alone. (1) Its first record is its `start` as §5.10 defines it: the record that carried its first event, or, for a segment with no event, its baseline record (the snapshot, or the first record after a clock cut). Its clock epoch starts at the last clock step (R3, below) at or before that record, or at the capture's first record when there is none; a segment never contains a later step, because a step cuts it, and a step between a baseline and the first event, while no segment is open, only moves the epoch. (2) Millisecond samples: every usable method response (above) that is the first response to a request of the segment's own socket, has the method that answers that request (§8.1, Subscription identity), and whose request record and response record both lie on that socket, at or after the later of that socket's `ws_open` and the start of the epoch, and at or before the segment's end record (`capture.endRawRecord`). The acknowledgements of the socket's three initial subscriptions always precede its subscription gate and therefore the segment (§5.3); they count for every segment of that socket in the same epoch, as do the acknowledgements of resync requests and the pongs up to the segment's end. (3) REST probes: every usable `probe` record that lies in the epoch at or before the segment's end record, was received (`recvMonoNs`) no more than 15 minutes before the segment's first record, and, when the epoch starts at a clock step, was sent (`sentMonoNs`) no earlier than that step's record. No sample of another socket, none recorded after the segment's end and none across a clock step is used, so the offset of a segment never mixes two wall-clock settings. Which responses carry `time_in` and `time_out` is venue behaviour this contract does not assume (M2_DATA_SOURCE_DECISION.md §2, row "venue timestamps"; §4 lists the pages the owner reads): if the acknowledgements carry them, as a documentation excerpt shows [S], every segment of a socket on which no clock step occurs from the first of its three initial `subscribe` records to the segment's end owns at least three; if no response carries them, every segment that owns a probe is `rest_time`, I6 fails its cells, and a segment that owns no probe is refused. `tests/capture-structure.ts` (`ownedClockSamples`, and `clockEstimate` for the values) is the executable reference for this rule (§5.11).
- **Negative lag floor.** If more than 0.1% of a segment's events have `obsTime < marketTime`, the segment is refused (R2). The remaining few are left as they are and the engine rejects them (`invalid_timestamps`), which the ledger records. `obsTime` is never shifted.
- **Wall-clock steps.** For consecutive raw records (across file rotation; the normalizer carries the previous file's last clocks itself), let `Δwall = recvWallMs[i] - recvWallMs[i-1]` and `Δmono = (recvMonoNs[i] - recvMonoNs[i-1]) / 1e6`. Any `Δwall < 0`, or `|Δwall - Δmono| > 10` ms, is a clock cut (R3) at record `i`: the segment ends at record `i-1`, and record `i` is the first record of the next segment (`startReason: resync_after_clock_cut`), whose baseline is the carried-over verified book (no fresh snapshot is needed because every later update is verified on its own; the segment's first book event is the first verified update after the cut, and trades before it are `dropped.tradeWhileUnsynced`, §5.3, §5.8). `recvMonoNs` must be strictly increasing; a non-increase is R1b.
- Different venue streams may carry different venue clocks; the adapter states which field it uses per stream and the header records both names (§8.5).

### 5.7 Duplicates

- **Book.** No sequence number appears on book messages in any official type or fixture [R], and none was located in the documentation [U], so a duplicated update cannot be identified as such; an idempotent re-send applies to the same state, verifies against its checksum and is emitted as what the feed delivered. `dropped.depthDuplicate` is always 0 for this adapter; the key is reserved for adapters with sequence numbers (the schema constrains the values of `dropped`, not its keys).
- **Trades.** `tradeId` is the venue's `trade_id`, which a search excerpt of the venue's documentation describes as a sequence number unique per book [S] (`tradeIdOrdered: true`; the owner's reading of that wording is still outstanding, decision §4). A trade whose id equals one already emitted in the segment is `dropped.tradeDuplicate`; a lower id is `dropped.tradeIdRegression`; an id that skips ahead is counted (`tradeIdJumps`) but is not a cut, because no source read documents contiguity [U], and it must not be invented.

### 5.8 Gaps, cuts, segments and reconnection

- **One socket per segment.** Each socket's records run from its `ws_open` to its terminal record, the last record its settlement writes (§8.1), and the records of a two-record settlement are consecutive: no record of any kind, a file rotation included, lies between them (R10). A segment's records all lie on one socket, after that socket's subscription gate record (§5.3) and before the first record of its settlement, which ends the segment (a cut, or the planned end); no later record of that socket and no record of another socket is part of it, so no segment spans a settlement and none covers a socket before its gate. A socket that R9 refuses yields no segment of any kind (no written, too-short or refused segment) and uses no segment index. `tests/capture-structure.ts` (`analyzeCapture`) gives, for every socket, the only records a segment of it may cover (§5.11).
- A cut is any of the following revealed while a segment is open: a checksum mismatch (§5.3), a crossed or malformed book (R6), a snapshot (reset), a `ws_close` or `ws_error` other than one whose `detail` is `capture_end` or `operator_stop`, or a clock step (R3). The segment then **ends at the raw record immediately before the record that revealed the condition**: every event carried by earlier records is emitted (trades between the last applied update and the revealing record included; they are matched against the last verified book, as any inter-update trade is), and `capture.endRawRecord` is that index. No book event is emitted from unverified state and nothing after the cut is attached. The same condition revealed while no segment is open (before a socket's subscription gate, §5.3 First event; after a cut before the next segment starts; or between sockets) is no cut, is listed in neither `capture.cuts` nor the normalize report's `cuts`, and changes no start reason: a checksum mismatch or a crossed or malformed book still invalidates the local book (§8.2 step 1), and a clock step keeps it. Of a settlement that writes two records (§8.1), only the first can cut; the second, and every lifecycle record written while no segment is open (`connect_failed`, `connect_timeout`, `reconnect_budget_exhausted`, the terminal record of an R9 socket or of a socket whose segment was already cut), is no cut, is listed in neither `capture.cuts` nor the normalize report's `cuts`, and ends nothing.
- **One record, several conditions.** When one raw record reveals more than one of these conditions (a clock step first visible on a `ws_close`, for example, or on a mismatching update), the segment ends once, at the record before it, with the first reason in this order: `capture_end`, `gap_disconnect`, `checksum_mismatch`, `malformed_depth`, `reconstruction_failure`, `snapshot_reset`, `clock_cut`; `capture.cuts` lists that one cut (none for `capture_end`). Each condition still has its own effect: one that invalidates the local book (§8.2 step 1) leaves no book to carry over, so a clock step on the same record opens no segment with a carried-over baseline; a lifecycle record still settles its socket; and a snapshot still replaces the book.
- After a reconnection or resubscription the venue sends a fresh snapshot; the normalizer starts a **new segment** at the first verified update after it (new fixture file, `segmentIndex + 1`). Segments are never stitched.
- Segment reasons. `endReason` is one of `capture_end`, `checksum_mismatch`, `snapshot_reset`, `gap_disconnect`, `clock_cut`, `reconstruction_failure` (a baseline never followed by a verified update, a crossed book), `malformed_depth`, and `gap_sequence` (reserved for adapters with sequence numbers; never produced by this adapter). A `ws_close` or `ws_error` whose `detail` is `capture_end` or `operator_stop` (the planned end or an operator stop, §8.1) ends the last segment with `endReason: capture_end` at the record before it without being a cut: it appears in neither `capture.cuts` nor the normalize report's `cuts`. A segment cut by any other lifecycle record ends with `gap_disconnect`. `startReason` of the next segment is `capture_start` for the first segment, `resync_after_clock_cut` after `clock_cut`, and `resync_after_gap` after every other reason. Every cut is listed in `capture.cuts` with `{reason, fileIndex, record, detail}`.
- Trades observed while no verified book exists (before the first verified update of a segment, or after a cut until the next one) are not emitted; they are counted (`dropped.tradeWhileUnsynced`).

Every dropped or cut item of a run that segments the capture is counted in the header (`capture.dropped`, `capture.cuts`) and listed with raw record indices in the normalize report (§5.10), so nothing disappears silently.

The raw-record schema enforces each record's shape and the lifecycle `detail` vocabulary only; it cannot see order, pairing or the number of settlements of a socket (it accepts, for example, a second terminal record, which R10 refuses, and `ws_close` `remote_close:1006`, which the table rules out and no rule checks, since a close code is not compared with how the close happened). Order and pairing are R10's, evaluated over the whole stream.

### 5.10 Normalize report (its data boundary)

Every normalization run whose raw `manifest_start` is readable (the first record of file 0 parses as JSON with `type: "manifest_start"`, a `captureId` that is a lower-case UUID version 4 and an integer `captureFormatVersion` of at least 1) writes one report, `<captureId>.normalize-report.json`, beside the fixtures it writes (`<captureId>-seg<segmentIndex>.jsonl`; a report's `fixtureFile` is exactly that name for its own `captureId` and `segmentIndex`), also when it writes none; a run whose `manifest_start` is missing or not readable in that sense writes no report and exits with an error naming the field (R1); a run refused because the report its `--supersedes` names fails the report check or carries another `captureId` (below) writes nothing, neither a fixture nor a report, and exits with an error; and a run stopped by a failed `obsTime` assertion (§5.2) writes nothing either. Its format is `schemas/normalize-report.v1.schema.json` (`reportFormatVersion: 1`). The schema is closed: every object rejects undeclared properties, its maps take only the keys this contract names, and every value is of one of the kinds below; no value of another kind fits, which does not keep a recorded value out of these kinds (last paragraph of this section).

- Counts: non-negative integers under the named `dropped` keys (`depthBeforeSnapshot`, `depthWhileUnsynced`, `depthBeforeSubscribed`, `deleteOfUnknownLevel`, `depthDuplicate`, `exponentLexemeInBook`, `tradeSnapshotHistory`, `tradeOffBook`, `tradeWhileUnsynced`, `tradeDuplicate`, `tradeIdRegression`, `foreignSymbol`, `offTickPrice`, `offLotSize`, `nonPositiveTradeSize`, `undecodable`, `socketNotSubscribed`), each with the raw record references of the records that carried the dropped items, and under `counts`: records by type (`records.<type>` for the thirteen record types of §4.1) and taker order types (`trades.ordType.limit`, `trades.ordType.market`, and `trades.ordType.other` for any other value, which is counted and never named, §8.3). A run that segments the capture carries every named `dropped` and `counts` key, with count 0 and `records: []` when nothing was counted; a run refused at capture level carries `{}` for both.
- Reason codes and rules: each segment's status (`written`, `too_short`, `refused`), start and end reasons (§5.8), the rule that refused a segment (R2, R2b, R6 or R7), cut reasons, and the rejection rules `R1` to `R10` with their scope (`capture`, `socket`, `segment`, `item`) and, where a rule names a field (R1, R4, R5, R8), the field's name from a fixed list (`manifestEnd`, `captureFormatVersion`, `capturer`, `recvWallMs`, `recvMonoNs`, `price`, `size`, `pair`, `priceDecimals`, `qtyDecimals`, `priceIncrement`, `qtyIncrement`, `instrumentSpec`, `status`, `rights`). R5 names `instrumentSpec` when the specification is missing from the manifest or the instrument channel (a capture with no instrument snapshot included), `pair` when the pair is, `status` for a status other than `online`, and otherwise the field whose value exceeds the engine's scale, disagrees between the sources or changes, the first that applies of `priceDecimals`, `qtyDecimals`, `priceIncrement` and `qtyIncrement`. An R9 socket is one rejection with scope `socket` and the record of its `ws_open`; it adds no segment and uses up no segment index. An R4 item is counted under its one `dropped` key (`foreignSymbol`, `nonPositiveTradeSize`, `offTickPrice`, `offLotSize` or `undecodable`, in the precedence of §5.5), whose `records` list the record that carried it; for each field its R4 items name (`pair` for `foreignSymbol`, `size` for `nonPositiveTradeSize` and `offLotSize`, `price` for `offTickPrice`, none for an undecodable frame), that record gives one rejection with scope `item` and that record as `at`, however many of its items name that field, so a frame carrying two off-lot trades is `offLotSize` `count` 2 with one record reference and one rejection, and every record listed under those keys has its rejections. An R4 rejection's `segmentIndex` is the index of the segment whose span (its `start` to its `end`, inclusive) contains that record, or null when no segment's span does. A cut (§5.8) is reported only in `cuts` and adds no rejection, so R3 never appears in `rejections`; R6 appears there, with scope `segment`, only when it refuses a segment, as R2, R2b and R7 do for the segments they refuse. Each rule has one scope (R1, R1b, R5, R8 and R10 `capture`; R9 `socket`; R2, R2b, R6 and R7 `segment`; R4 `item`), names only its own fields (R1 a manifest or record field, R4 `pair`, `price` or `size` or none, R5 an instrument field, R8 `rights`; every other rule none), a `too_short` segment is refused by R7 and a `refused` one by R2, R2b or R6, and the repository rule checks these pairings (§6.5). A run refused by a rule with scope `capture` (R1, R1b, R5, R8 or R10) reports that rule with scope `capture` and lists no segments, cuts or dropped items (`segments: []`, `cuts: []`, `dropped: {}`, `counts: {}`, and only capture-scope rejections): once a capture-scope rule applies, the normalizer does not segment the capture, so the segment rules R2, R2b, R6 and R7 are not evaluated and no segment index is used.
- Raw record indices: `{fileIndex, record}` references into the raw files. A segment's `start` is the record that carried its first event or, for a segment with no event, its baseline record (the snapshot, or the first record after a clock cut, §5.6); its `end` is `capture.endRawRecord` (§5.8); `events` is the number of events it holds, or would have held when it is refused or too short. `rawFiles[].records` is the number of complete records before the file's `file_end` (all of them when it has none). A rejection's `at` is the record that revealed the condition: for R1 the record lacking the field, or `manifest_start` for a manifest field; for R1b the first record out of order or out of range, the first record after a file's `file_end` that should not be there, or the file's `file_end` for a hash mismatch; for R4 the record carrying the item; for R6 (a refused segment) the record that revealed the condition; for R9 the socket's `ws_open`; for R10 the offending record, except that for records after `manifest_end` it is the `manifest_end` record. Every reference therefore lies at most one record past its file's `file_end` (the repository rule checks that bound, §6.5). `at` is null for R2, R2b, R5, R7 and R8, which name no single record.
- Hashes (lower-case hex): `rawFiles[].sha256` is the SHA-256 the normalizer computes itself over the bytes §3 names (every byte before the file's `file_end`, or every byte of the file when it has none), never a value a `file_end` or `manifest_end` declares, also when R1b refuses the capture; `segments[].fixtureSha256` is the written fixture's `fixtureContentHash` (§3), the value its ledgers record as `replay_started.fixture.contentHash`, and `supersedes` compares that value.
- The run's options (`depth`, `minWindows`, `windowMs`) and version and provenance metadata: `captureId` (a lower-case UUID), the `captureFormatVersion` the raw manifest declares (also when it is unsupported, R1), `fixtureSchemaVersion`, the normalizer's name (`markout-ledger`), version and commit, the adapter's name (`kraken-spot-ws2`, §8) and version, and each written fixture's file name.
- `supersedes`, only when the run is given `--supersedes <earlier report>`: that report's written segments whose fixture hash this run does not reproduce, each with its segment index and hash and the earlier run's normalizer version and commit and adapter version. The normalizer reads no report other than the one `--supersedes` names, which may lie in `--out`: it reads that report before it writes anything and refuses the run if the report fails the repository rule's report check (§6.5: the closed schema, canonical bytes, order, pairings and cross-references; the same function, `classifyNormalizeReport`) or carries a different `captureId`. A `supersedes` entry never repeats the segment index and hash of a segment this run wrote. It never looks in `--out` for reports on its own, so the report is a function of the raw files, the adapter version and the options, and of the earlier report only when that option names it.

The report's bytes are canonical: every object's keys are in ascending order (all keys are ASCII), arrays are in a fixed order (`rawFiles` by `fileIndex` from 0 with no gap; `segments` by `segmentIndex` from 0 with no gap; `cuts` and each dropped entry's `records` in strictly ascending raw-record order, so each carrying record appears once and `records` holds at most `count` entries; `rejections` in strictly ascending order of `at` (those without one first), then `segmentIndex` (none first), then rule and field, each in the order the schema lists them; `supersedes` by strictly ascending `segmentIndex`), and it is written as `JSON.stringify` of that value with an indent of 2, followed by one newline. A tracked report whose bytes differ from that serialization of its own content, or whose arrays break that order, fails the repository rule (§6.5), so neither a duplicated key (which JSON parsing would silently drop), nor whitespace, nor the order of keys or entries can carry anything. The report never carries a raw value: no price, size, lexeme, timestamp, trade identifier, venue status value or other field of a venue message, no excerpt of a payload, no free-text detail (the fixture's `cuts[].detail` stays in the fixture), and no clock, lag or offset value (those are derived values of the fixture header, published only as A12 reports them). What an error message prints on the operator's console (R5 names both values) stays on that console and never enters the report. Which rule governs a value depends on what the value is, never on where it appears. A recorded market observation (a price, size, lexeme, timestamp or trade identifier of a book or trade message, or any excerpt of a venue payload) is recorded data wherever it is published, in a report, a pull request or a document: that is gate (b)'s use, excluded until it is itself cleared, expressly and by name (M2_DATA_SOURCE_DECISION.md §1). An instrument reference value (a pair name, precision, increment or status value, `venueStatus` values included) is a use (iv) output wherever it appears, also when copied verbatim from the instrument payload, published only as far as the attested clearance names it, as it must for P0 and A12; a copy of several fields of a payload together is an excerpt, and so recorded data. A receive-clock value that dates one observation (an event's `obsTime`, a raw record's `recvWallMs`, a fixture's `startTime` or `endTime`, `risk.killSwitchAt`) is treated as recorded data, since it tells when that observation was made, unless the attested clearance names it expressly; a duration or offset derived from such values (a lag statistic, a clock offset, a time measured from the fixture's start) is a use (iv) output. The normalize report carries neither kind itself; its rules and field names can still state that a value failed a check (R5 with field `status` says the pair was not `online`), which is part of what use (iv) clears. A report is published only as far as the attested clearance of C2's use (iv) covers it. The report is deterministic (A1): the same inputs give a byte-identical report, so it holds no run time and no host name. What the schema, the byte check and the repository rule's cross-reference checks (§6.5) cannot rule out is a recorded value encoded into one of the report's constrained values: an integer placed in any integer field (a count, an index, an option or `captureFormatVersion`; the rule bounds every number to a safe integer written in plain digits and every raw record reference to the files the report lists, which narrows this channel without closing it), the number of entries in an array, the choice among the enumerated codes a value may take (a reason, or a rule with its allowed scope and fields) or between null and a value where the rules leave that choice, bytes hex-encoded into a hash, UUID, commit or version string, whether `supersedes` is present (it says whether `--supersedes` was given) and whether it is empty, and the directory in which a report is committed and how many reports of one capture are committed. The cross-reference checks test consistency, not truth. Review remains the control for all of these.

### 5.11 Executable reference for the structural rules

`tests/capture-structure.ts` states the structural rules of §5.3 (the subscription gate), §5.6 (sample ownership), §5.8 (one socket per segment), R5, R9 and R10 of §5.9, and §8.1 (request, subscription and instrument identity) as code over parsed raw records: for a capture it returns the capture-level refusal, if any (R1b, R5 or R10, with the record at which it found it; the normalize report names R5 by rule and field only, §5.10), and for every socket its span, settlement, gate, R9 verdict and the only records a segment of it may cover; it also lists the trade items of another pair that are `dropped.foreignSymbol` and the book messages of another pair inside a window, and returns the clock samples a given segment owns and the `venueClockOffsetMs` values computed from them. It is a reference, not a normalizer: it builds no book, verifies no checksum and emits no event. `tests/capture-structure.test.ts` holds its vectors, each a raw stream valid against `schemas/capture-record.v1.schema.json`, among them the interleavings that motivated these rules (records between the two records of a settlement, a new socket's records before its acknowledgements, an acknowledgement or a subscription for another pair, a reconnection's instrument snapshot without the pair, and a clock step between a socket's acknowledgements and a segment). PR-1's normalizer must reach the same verdicts on every vector (handoff A7(r)); where the two disagree, this contract decides and both are corrected in the same pull request.

## 6. Fixture schema v2 (versioned changes to the JSONL schema)

Supported schema versions become `[1, 2]`: version 1 is the existing synthetic format, which the synthetic generator and the test helpers keep writing unchanged (the committed fixtures stay byte-identical); version 2 is required for `synthetic: false`. The header type becomes `schemaVersion: 1 | 2`; the v2 rules below apply only when `schemaVersion === 2`, and the synthetic-label check stays first. Valid version-2 headers (recorded at both quantity scales, and synthetic) and events are in `schemas/examples/fixture.v2.examples.json` (constructed values, not venue data), validated with derived failure cases by `tests/schemas.test.ts`.

Unknown properties. The raw-record and fixture schemas accept properties they do not declare, so that additive optional fields can be introduced without a version bump (§9); the engine ignores them. `fixtureContentHash` covers undeclared header properties (the header is hashed as parsed), but the loader's `fromWire` drops undeclared event properties and the hash is taken over `toWire`, so they are not hashed: a new event field must be declared and round-tripped (as S3 does for `venueSeq`, `rawRef` and `recvMonoNs`, §6.2) before a normalizer writes it. Raw records other than `file_end` and `manifest_end` are covered by their file's SHA-256 (§3); those two records, and any undeclared property on them, are not hashed. Two places are closed to unknown keys because this contract excludes content from them: the raw manifest's `host` block (only `os` and `runtime`, never the capture host's hostname or address, §4.1) and the fixture's `clockReports` with its `start` and `end` blocks (parsed fields only, never the verbatim report, §4.2). For the same reason the normalize report's schema is closed throughout (§5.10), and the `detail` of `ws_open`, `ws_close` and `ws_error` takes only the values of the lifecycle table of §8.1. A schema checks the presence and shape of a field, never whether what it says is true (§6.3).

### 6.3 `rights` block and the publication gate

```json
{"termsUrl": "...", "termsCheckedOn": "YYYY-MM-DD", "checkedBy": "<person>", "redistribution": "permitted" | "prohibited" | "unclear", "publication": "hash_only" | "sample_permitted", "note": "..."}
```

The block is supplied to the normalizer as a file (`--rights <path>`); it is not part of the raw capture. `termsUrl`, `checkedBy` and, when present, `note` must be non-blank: each must contain at least one character that is a letter, number, punctuation mark or symbol (Unicode general categories L, N, P and S) and is neither a default-ignorable code point nor one of the blank glyphs U+2800, U+303F, U+FFFC, U+13441, U+13442 and U+1D159. Values made only of whitespace (every Unicode White_Space character, U+0085 and U+00A0 included), separators, control or format characters (U+200B to U+200D, U+2060 and U+FEFF included), combining marks, default-ignorable fillers or those blank glyphs are therefore rejected (`$defs/nonBlank` of the fixture schema: an ECMAScript pattern with Unicode property escapes that must be evaluated with the `u` flag, as Ajv does by default, and whose character classes follow the Unicode data of the engine evaluating it). The rule concerns which characters are present: a value such as `x` passes, and no schema check says whether a value is true, meaningful or sufficient. A recorded fixture is committed to this public repository only when `publication` is `sample_permitted` **and** `redistribution` is `permitted`, with the terms URL and the date a person checked them, **and** its `note` identifies the owner's nonprivileged attestation on pull request #3 that records the clearance of publishing recorded data under decision condition C2 (its date, source, scope and outcome); a person's own reading of the terms never establishes `permitted`, and the schema requires `note` whenever `redistribution` is `permitted`. **Schema validation checks the note's presence and shape only.** It cannot establish that the attested record exists, that it is Kraken's written permission, or written clarification concluding that the use is permitted, or a route (b) opinion meeting decision §1 C2 for publishing recorded data, or that it clears the scope claimed; the owner verifies that substance manually before any recorded fixture is committed, and a passing schema check or repository test is never that verification. Everything else stays outside the repository; the repository and its pull requests carry the fixture's content hash, the raw files' hashes, the normalize report (§5.10) and derived values, each only as far as the attested clearance of decision condition C2's use (iv) covers it. Three rules, each independent of the others. Nothing is captured until decision conditions C2, C3 and C5 are met (M2_DATA_SOURCE_DECISION.md §1; C5 is the owner's dated reading of the live pages M2_DATA_SOURCE_DECISION.md §4 lists, among them those behind `tradeIdOrdered`, `per_fill` and the 15 s liveness timeout). Until publishing recorded data is itself cleared in writing, expressly and by name, under the C2 routes and test, the only admissible block for this venue is `redistribution: "unclear"` or `"prohibited"` with `publication: "hash_only"` (decision §2, "publishing samples"). Raw captures never enter Git, whatever the rights block says: `.gitignore` excludes the default output directories `captures/` and `normalized/` from this PR on, and §6.5 states which checks detect a violation of that rule and what, if anything, prevents one.

### 6.4 Validation additions

`validateHeader`: version 2 requires `depth`, `venueSymbol` and both `timeBasis` strings; `synthetic: false` requires version 2, `provenance.source === "recorded"`, `provenance.recordedFrom`, `provenance.captureMethod`, `provenance.capture`, `provenance.instrumentSpec` (with `integrity`), `provenance.rights`, and `provenance.timeBasis.obsTime === "capture_receive"` (`third_party_receive` rejected as not implemented). Version 1 keeps today's rules for synthetic fixtures; a version-1 header with `synthetic: false` is rejected from this build on (recorded data requires version 2), which today's code accepts, so EVENT_SCHEMA.md records it as a versioned validation change. ### 6.5 Repository hygiene (A10): the tree under test, commit history and prevention

**The rule** (`tests/jsonl-policy.ts`, handoff A10) covers three kinds of path, in any letter case, fails closed on every covered file it cannot classify, and checks the content of every other tracked file that is text:

- any path under a directory named `captures` or `normalized`, at the root or at any depth: never allowed (both are the default output directories of the capture and normalize tools and `.gitignore` ignores them at any depth, so a file there is tracked only by force);
- a name ending in `.normalize-report.json`, in any directory: its file name must be exactly `<captureId>.normalize-report.json` for the `captureId` it carries; it must validate against the closed report schema; its bytes must be its canonical serialization; every number in it must be a safe integer (at most 2^53 - 1, so it is written in plain digits); its arrays must be in the canonical order; each `fixtureFile` must name its own capture and segment; each rule must carry its own scope and fields; and its cross-references must agree (§5.10): every raw record reference names a listed raw file and a record at most one past that file's `file_end` (the record R1b names when one follows it, or, in the last file, `manifest_end`), each segment's `start` is not after its `end` and segments do not overlap and follow raw order, the first segment starts with `capture_start` and each later one with `resync_after_clock_cut` exactly when the one before ended with `clock_cut`, only the last segment ends with `capture_end`, each refused or too-short segment has exactly one segment rejection and a written one none, each cut names a listed segment, at most one cut names a segment, a cut's reason is its segment's `endReason` and its record follows that segment's `end`, a rejection's `at` is null exactly for R2, R2b, R5, R7 and R8, each R4 rejection's record and field match the records of its `dropped` key and its `segmentIndex` is the segment whose span holds that record (or null), and no `supersedes` entry repeats a segment this run wrote. It does not check the rest of §5.10's semantics (whether a segment whose end reason is a cut reason has its cut, whether record-type counts add up to the raw files' record counts, or which rule, reason or field a condition deserved);
- a name ending in `.jsonl`, in any directory: it must be one of two kinds. (1) A version-1 synthetic fixture in the engine's own format: its header carries only the version-1 header keys of EVENT_SCHEMA.md and the synthetic generator's provenance keys, each with its version-1 type (strings; integers for the scales, the times, `eventCount` and `seed`), with exactly `synthetic: true`, `provenance.source: "synthetic"` and the synthetic label; the engine's parser accepts the whole file; every trade's `aggressor` is `buy`, `sell` or `unknown`; and the engine's serializer reproduces the file byte for byte, so no line carries a key, value type or byte outside that format. (2) A version-2 recorded fixture whose header matches `$defs/header` of `schemas/fixture.v2.schema.json` with `synthetic: false` and a rights block of `redistribution: "permitted"` with `publication: "sample_permitted"` (so a non-blank terms URL, check date, checker and note), whose every following line matches `$defs/event`, and whose `eventCount` matches. Everything else fails: a raw capture record on any line (its `type` is a record type of `schemas/capture-record.v1.schema.json`, or it carries both `recvWallMs` and `recvMonoNs`); a line that is not valid JSON or not a JSON object; a first non-blank line that is not a fixture header (unwrapped venue frames, and events or other objects without an allowed header); a version-1 header that is not synthetic; a version-2 synthetic header (the generator writes version 1); a recorded fixture without that rights shape; any other schema version; and an empty file. Blank lines are skipped when classifying, as the engine's parser skips them, but a synthetic fixture that contains one fails the byte-for-byte check. Files are read literally as paths and decoded as strict UTF-8: bytes that are not UTF-8 fail, and a leading byte order mark is kept, so JSON parsing rejects it. A covered path that is a symbolic link or a submodule entry fails, whatever it points to, in the tree under test and in history alike.
- every other tracked regular file, and every commit message in the history scan: if its bytes are UTF-8 text, no line of it, trimmed, may be a JSON object that is a raw capture record (as defined for kind (2) above), whatever the file's name (`.ndjson`, `.json`, `.txt`, `.log`, `.csv`, or a name with no extension). In the history scan and the hook it also reads each commit's header, where merging a signed tag copies that tag's message (`mergetag`). This content check finds a raw capture written one record per line under any name, and nothing else: it does not see a record spread over several lines, embedded in other text on its line, encoded (base64, for example), compressed, or in a file that is not UTF-8 text, which it does not inspect, and it does not see recorded data in any other form (below).

**Three layers**, which differ in what they can do:

1. *The tree under test* (`tests/repository-jsonl.test.ts`, in `npm test` and CI). It lists the tracked files with `git ls-files` (in a git checkout a failure of that listing fails the test) and checks every covered file. Where the root has no `.git` (an exported archive) it scans the file tree instead, skipping only the root's `.git`, `node_modules`, `out` and `dist`, so a file force-added under one of those is not seen in that mode; a directory at a covered path (how `git archive` exports a submodule entry) is listed and fails; and every file under `captures/` or `normalized/` fails. It sees only the files present where it runs: a file added in one commit and deleted in a later one is invisible to it.
2. *The commit range* (the CI step "A10 history scan", `npm run test:history`, `tests/a10-history-cli.ts`). It scans the tree of every commit of a pull request's range (`base..head`) or, for a push to `main`, of that push's range (`before..after`; an all-zero base scans every commit reachable from the head), oldest first, with the same rule, so a disallowed file added and deleted again inside the range is found and named with the commit that brought it in; a disallowed file the base already carries is reported too. When the base commit is not in the checkout (the `before` of a force-push to `main`, for example), the step scans every commit reachable from the head instead, and says so. The step fails when the range cannot be listed or a file cannot be read. CI is triggered by nothing else: a branch pushed without an open pull request, any tag, and any other ref (git notes, for example) are scanned on GitHub by no layer, a branch only if and when a pull request is opened from it; commits that are force-pushed away, or whose branch is deleted, before a pull request is opened are never scanned, and GitHub may keep them retrievable by their SHA; only the opt-in hook can cover such a push. GitHub also starts no run for a push, or a pull request head, whose commit message carries a skip instruction (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]`, or a `skip-checks: true` trailer), for a pull request with a merge conflict, or for a fork pull request awaiting approval; a pull request's next run rescans its whole `base..head`, but a skipped push to `main` is in no later push's `before..after`, so its commits are scanned again only if a later push's base is missing from the checkout and the step falls back to every commit reachable from the head. It detects; it does not prevent: it runs after the push, when the commits and their files are already on GitHub. A file it finds has been published: removing it takes a rewrite of the branch's history and a force-push, and whatever GitHub, a fork, a clone or a cache retained in the meantime is outside this repository's control. The owner decides the response; nothing here claims that removal undoes a publication.
3. *Prevention, opt-in and local* (`.githooks/pre-push`). Installed once per clone by copying it into that clone's own hooks directory (`cp .githooks/pre-push .git/hooks/pre-push && chmod +x .git/hooks/pre-push`, after `npm ci`), it stays active whatever commit is checked out, and it refuses the push when it cannot run: without `node_modules`, or from a checkout that lacks the scan (`tests/a10-history-cli.ts` and `tests/jsonl-policy.ts`, which it runs from the working tree). The copy is frozen when it is made, so it also refuses the push while the checkout's own `.githooks/pre-push` differs from it, until it is copied again. Every git command it and the scan run ignores replace refs (`GIT_NO_REPLACE_OBJECTS`), so they read the objects a push sends. Enabling it with `git config core.hooksPath .githooks` instead is weaker: that path is resolved against the working tree, so while a commit without `.githooks/pre-push` is checked out (`main` before pull request #3 is merged, or any older commit) there is no hook and pushes go through unscanned. It runs the same scan over the commits of each pushed ref (for a ref the remote already has, those between the remote's value and the pushed commit, or, when the remote's value is not in the clone (a force-push after a history rewrite, or without a prior fetch), every commit reachable from the pushed commit, and it says so; for a new remote ref, every commit reachable from the pushed commit, since the clone's remote-tracking refs may be stale) and refuses the push if any of them carries a disallowed file, or if a pushed ref does not point, directly or through an annotated tag, at a commit. It is the only layer that acts before anything is sent, and only where it is installed and not bypassed: `git push --no-verify`, `-c core.hooksPath=<elsewhere>`, a clone where it is not installed, a checkout without the hook while it is enabled through `core.hooksPath`, an edited or non-executable hook, another git client, and an upload through the GitHub web interface or GitHub's content APIs all skip it. It scans the commits of every pushed ref (a git notes ref's notes are files of its commits, so the content check reads them), their commit messages and headers, and the message of every annotated tag it pushes. The owner installs it in `.git/hooks` of every clone on the capture host before the first capture (handoff A12); no test can verify that step.

No server-side control is claimed, and none of the three layers is complete prevention: these documents configure and verify no GitHub push restriction, ruleset or code-owner review for this repository; whether to add one (for example a ruleset, or required review of the four files named below) is the owner's decision, not made here. What no layer sees: anything published outside git, which no layer reads (a pull request's description, comments and reviews, where A12's evidence and the P0 statement go; issues; the repository wiki; releases and their assets; CI artifacts), for which the owner's review before posting is the only control; whether the attested clearance exists or covers a fixture; whether a file declared synthetic is in fact synthetic (recorded observations re-encoded in the version-1 format and labelled synthetic pass kind (1)); a venue payload pasted into a string value of either fixture kind or into an open object of a recorded fixture; a recorded value encoded into a normalize report's constrained values (an integer in any integer field, the number of entries in an array, the choice among the enumerated codes a value may take, or bytes hex-encoded into a hash, UUID, commit or version string); recorded data in a file whose name matches none of the three kinds, or in a commit or tag message, in any form other than a raw capture record on a line of its own: a recorded fixture of any rights shape named `.ndjson`, `.json` or `.txt`, unwrapped venue frames, a normalize report under a name that does not end in `.normalize-report.json` (such as `normalize-report.json`), CSV or other exports of recorded values, and a raw capture record spread over several lines, embedded in other text, encoded, compressed or in a file that is not UTF-8 text; a recorded value encoded into a normalize report in the other ways §5.10 lists (the choice between null and a value, whether `supersedes` is present and whether it is empty, the directory a report is committed in and how many reports of one capture are committed); a tag message or a git note pushed without the hook; and a change to the checks themselves: every layer runs the rule (`tests/jsonl-policy.ts`) and the scan (`tests/a10-history-cli.ts`) of the working tree or commit under test, CI runs the `.github/workflows/ci.yml` of that commit, and the hook is the copy installed in the clone (or, through `core.hooksPath`, the checked-out `.githooks/pre-push`), so a pull request that weakens the rule, the scan or the workflow step passes under its own weakened version. The owner's manual verification and review remain the controls for those, and a pull request that changes any of those four files is reviewed for that change. Once the engine's version-2 parser exists (handoff S3), PR-1 extends kind (2) so that a recorded fixture must also load through it and re-serialize byte for byte, as kind (1) already must; until then a recorded fixture passes with any byte formatting and a duplicated JSON key counts with its last value, so that extension must land before any recorded fixture is committed.

### 8.1 Endpoints, subscriptions and live behaviour

Request identity. The runner numbers its requests 1, 2, 3 ... across the whole capture and never reuses a value: every `subscribe`, `unsubscribe` and `ping` record's `req_id` exceeds every earlier request's `req_id` (R10). A method response answers the request that carries its `req_id` on the same socket, once: a response on another socket, or with a `req_id` no request of its socket carries, answers nothing and counts for nothing (no acknowledgement, no clock sample), and a second response to a request already answered refuses the socket (R9), because whether the venue ever sends one is unknown [U].

Subscription identity. Every request's text is, byte for byte, its row above for the selected instrument with `<n>` replaced by its `req_id` written in decimal digits (no sign, no leading zero); any other text, one without a `req_id` included, refuses the socket (R9), and only a request that matches its row counts under Request identity. The method that answers `subscribe` is `subscribe`, `unsubscribe` answers `unsubscribe`, and `pong` answers `ping`. A response answers its request only if its `method` is that one and each echo it carries of what the request named equals it: `result.channel` the request's channel, `result.symbol` the selected instrument on a `book` or `trade` acknowledgement, and `result.depth` 100 on a `book` acknowledgement. What a request did not name is not compared (a symbol on an `instrument` acknowledgement, a depth on a `trade` one), since whether the venue echoes such fields is unknown [U]. `result.symbol` is optional in the official CLI's model of an acknowledgement [R `kraken-cli` `crates/kraken-core/src/response/result.rs:47-55`], so an absent echo is no mismatch, while an echo that differs is. A response with another method, or that names another channel, symbol or depth, is a mismatch: the runner treats it as no answer, so that subscription's acknowledgement timer settles the socket (`subscribe_ack_timeout`), and the normalizer refuses the socket (R9) whatever follows. The acknowledgement that counts for a socket's subscription gate (§5.3) is the one that answers the socket's initial subscription of that channel; a resync's `subscribe` is not initial.

Instrument identity. Every socket's first instrument snapshot must carry the selected pair with status `online`. The capture's first instrument snapshot, on whichever socket it arrives (a socket closed before its snapshot, or an attempt that never opened, delivers none), completes the capture-start specification: a failure there is R5, and a capture with no instrument snapshot at all is R5 too. A failure in any later socket's first snapshot refuses that socket (R9). Every instrument frame on every socket, snapshot or update, that carries the pair must give it the capture-start `price_precision`, `qty_precision`, `price_increment` and `qty_increment`, compared by value, and a later snapshot on a socket must still carry the pair; otherwise the capture is refused (R5). Trade items and book elements are checked against the selected instrument too: a trade item of another pair is `dropped.foreignSymbol` (R4, §5.5), and a book element of another pair is malformed (R6, §8.2).

Connection budgets and timeouts. Everything below is measured on the monotonic clock (`process.hrtime.bigint()`), never the wall clock. A timer of d seconds fires when d seconds have elapsed since it started: an awaited frame that arrives earlier completes the wait (a snapshot 9.999 s into a 10 s timer, for example), and one that arrives at d seconds or later is too late. A tie is decided by the frame's own receive clock, not by which callback the runtime runs first. The frame handler takes both clocks as its first action (§2), appends the frame verbatim as its `message` record, and only then compares the frame's `recvMonoNs` with every deadline armed on that socket and with the capture's planned end (Planned end and operator stop, below): a timer whose deadline is at or before that clock fires at once, before the frame is used for anything, so the frame satisfies none of the waits it arrived too late for, and the timer's lifecycle records follow the frame's `message` record in the file. If the timer's own callback runs first, it settles the socket (below) and writes its records, and a frame the runtime delivers after that is not received and is not written. Either way the wait has failed with the same records; only whether the late frame is in the raw file depends on the order in which the runtime delivers the two. A socket settled by `subscribe_ack_timeout`, `snapshot_timeout` or `instrument_snapshot_timeout` is an R9 socket in either order, whatever frames precede its terminal record (§5.9), and nothing after a terminal record is attached (§5.8). Otherwise, a frame the tie rule wrote before a timer's records or before the planned end's is part of the raw stream and is normalized like any other record: a book update or trade before `liveness_timeout` or `capture_end` is emitted, and a snapshot before `resync_failed` is a baseline that §8.2 step 7 refuses. The fixtures and the normalize report therefore depend on that order, as the raw file's hash and record counts do. Every other handler of a socket's runtime events (`open`, `error`, `close`), and the ping timer's callback, also reads the monotonic clock first and applies the same comparison: if a deadline armed on that socket, or the planned end, is at or before that reading, the timer settles the socket first and the event writes nothing of its own (a ping due then is not sent and no `ping` record is written; an `open` at the connect deadline writes no `ws_open`, only `ws_error` `connect_timeout`; a `close` at the liveness deadline writes only `ws_close` `liveness_timeout`).

- *Counting.* A resynchronization is counted once, when the runner sends its `unsubscribe`; the subscriptions sent on a newly opened socket are not resynchronizations. A reconnection is counted once, when the runner starts opening any socket other than the capture's first; a failed attempt (below) still counts, and every further attempt counts again. Each budget allows at most 5 of its kind in any sliding window of 300 s: at time `now` the window holds those counted at times `t` with `now - t < 300 s`.
- *Exhaustion.* Before sending a resync's `unsubscribe`, and before opening any socket after the first, the runner checks that budget. If 5 of that kind are already in the window, the budget is exhausted: the runner starts nothing further, writes a `ws_error` record whose `detail` is `resync_budget_exhausted` or `reconnect_budget_exhausted`, closes any socket still open (`ws_close`, detail `budget_exhausted`; the WebSocket close frame is the only frame it sends) and ends the capture, writing `file_end` and `manifest_end` as at the planned end. So the fifth within 300 s is performed and a sixth is never started; one needed exactly 300 s after the oldest in the window is performed, because that oldest has left it.
- *Resync.* The runner sends the resync's `subscribe` immediately after its `unsubscribe`, without waiting for the unsubscribe's acknowledgement, and starts the 10 s stalled-resync timer when it sends the `unsubscribe`. The resync completes when a book `snapshot` arrives before the timer fires. It fails when either request is answered with `success: false` or when the timer fires first. A failed resync stays counted in the resynchronization budget, closes the socket (`ws_close`, detail `resync_failed`) and escalates to a reconnection, which is subject to, and counted in, the reconnection budget. While a resync is outstanding (from its `unsubscribe` until the snapshot that completes it, or its failure), the runner's local book is unsynchronized: it applies no book frame and runs no live check on one (the clock-step rule of §5.6 still runs and still writes its `note`; every frame is still appended verbatim, and the normalizer drops those book frames, `dropped.depthWhileUnsynced`, §8.2), so a condition in a book frame of the old subscription starts no second resync and is not counted.
- *Every socket, the first included.* The runner starts a 10 s connect timer when it starts opening a socket; a socket that fails to open is a failed attempt (`ws_error`, detail `connect_failed`), and one that has not opened (`ws_open`) when that timer fires is aborted as a failed attempt (`ws_error`, detail `connect_timeout`); no `ws_close` is written for a socket that never opened. Once the socket opens, the runner sends the three subscriptions of this section at once, each starting its own 10 s acknowledgement timer. A `success: false` on any of them ends the capture: the runner writes `ws_error` (detail `subscribe_rejected`), closes the socket (`ws_close`, detail `subscribe_rejected`) and writes `file_end` and `manifest_end`, with no reconnection. An acknowledgement timer that fires before its subscription has been answered `success: true` closes the socket as a failed attempt (`ws_close`, detail `subscribe_ack_timeout`); an answer after that is not received. A 10 s snapshot timer starts when the book `subscribe` of those three is sent (a resync's `subscribe` is timed by the stalled-resync timer instead); if it fires before a book `snapshot` arrives, the socket is closed as a failed attempt (`ws_close`, detail `snapshot_timeout`). A 10 s instrument snapshot timer starts when the instrument `subscribe` is sent; if it fires before the instrument snapshot arrives, the socket is closed as a failed attempt (`ws_close`, detail `instrument_snapshot_timeout`). A 15 s liveness timer starts when the socket opens and restarts at every received frame; when it fires, the socket is closed (`ws_close`, detail `liveness_timeout`). A 30 s ping timer starts when the socket's `ws_open` is written and is cancelled when the socket is settled: a `ping` is sent, and its record written, only on the open, unsettled socket, never while a socket is connecting or after it is settled (the REST `Time` probe depends on no socket). "Open" here is the runner's state, from the socket's `ws_open` record until it is settled, not the runtime's `readyState`. After a close frame from the peer that is not followed by the end of the TCP connection (the observed case below), the runtime delivers no `close` event, so the socket stays open in that sense, and a `ping` is still sent and its record written although the runtime discards it; the liveness timer then settles that socket. A failed attempt, a timeout and any other close during the capture each escalate to one reconnection under the reconnection budget, a failure of the first socket included; that first socket is itself never counted. The runner starts each reconnection as soon as the records of the socket that requires it have been written, with no back-off delay, so a reconnection is needed and counted at the same instant.
- *Settlement: one set of records and at most one reconnection per socket.* Each socket the runner starts opening is settled exactly once, by the first condition of the table below to occur (a tie by the event's receive clock, as above; conditions due at the same instant in the order planned end or operator stop, connect, stalled resync, acknowledgement, snapshot, instrument snapshot, liveness). Settling writes that row's records, consecutively (a `note` the settlement calls for, such as a clock step, and a file rotation that falls due, follow its last record; nothing is written between them, R10; after a settlement that ends the capture, including one that an operator stop turns into the end, the runner writes no `note` and starts no rotation, and only `file_end` and `manifest_end` follow), decides what follows, detaches the runner's handlers from the socket and, if the socket is not already closed, closes it (code 1000). Nothing the runtime reports for that socket afterwards (a later `error`, `close` or `message` event) is received or written, and none adds a record or a reconnection. The table fixes every `detail` value of `ws_open`, `ws_close` and `ws_error`, and `schemas/capture-record.v1.schema.json` enforces them.
- *Planned end and operator stop.* The target duration (default 90 minutes, `--duration-min`) is measured on the monotonic clock from the `manifest_start` record. When it elapses, or when the operator stops the runner (SIGINT or SIGTERM), the runner settles the socket as the table's last row says, sends nothing further and writes `file_end` and `manifest_end`; when no socket exists at that instant it writes only those two. The signal handler, like every other handler, reads the monotonic clock first: a deadline armed on the socket that is at or before that reading settles the socket first with its own row's records, and the stop then ends the capture in place of that row's reconnection (no socket is opened after a stop). A REST probe whose response has not arrived when the capture ends is abandoned and writes no record, so nothing but `manifest_end` follows `file_end`. The normalizer ends the last segment at such a record with `endReason: capture_end`, and the record is not a cut (§5.8).

| socket state | first condition to occur | records written | then |
|---|---|---|---|
| connecting | the runtime's `open` event before the connect timer fires | `ws_open` (detail `open`); the three subscriptions are sent | not settled |
| connecting | the runtime's `error` or `close` event before `open` (a refused connection, a name-resolution, TLS or handshake failure) | `ws_error` `connect_failed` | reconnection |
| connecting | the connect timer | `ws_error` `connect_timeout` (the attempt is aborted) | reconnection |
| open | the runtime's `close` event with `wasClean: true` (the venue closed with a close frame) | `ws_close` `remote_close:<code>` | reconnection |
| open | the runtime's `close` event with `wasClean: false` (code 1006 included: the connection dropped without a closing handshake) | `ws_close` `connection_lost:<code>` | reconnection |
| open | the runtime's `error` event | `ws_error` `network_error`, then `ws_close` `network_error` | reconnection |
| open | a timer: stalled resync, snapshot, acknowledgement, instrument snapshot or liveness | `ws_close` `resync_failed`, `snapshot_timeout`, `subscribe_ack_timeout`, `instrument_snapshot_timeout` or `liveness_timeout` | reconnection |
| open | `success: false` on a resync's `unsubscribe` or `subscribe` | `ws_close` `resync_failed` | reconnection |
| open | `success: false` on one of the three subscriptions of a newly opened socket | `ws_error` `subscribe_rejected`, then `ws_close` `subscribe_rejected` | end |
| open | a resync is needed and its budget is exhausted | `ws_error` `resync_budget_exhausted`, then `ws_close` `budget_exhausted` | end |
| none open | a reconnection is needed and its budget is exhausted | `ws_error` `reconnect_budget_exhausted` | end |
| open or connecting | the planned end, or an operator stop | `ws_close` (open) or `ws_error` (connecting), detail `capture_end` or `operator_stop` | end |

"Reconnection" means the next socket is started under the reconnection budget (Exhaustion, above); "end" means the runner writes `file_end` and `manifest_end` and stops. What the runtime delivers is not part of this contract: whatever order or subset of these events it delivers, the first one settles the socket, so exactly one row's records and at most one reconnection follow; which row applies depends on which event the runtime delivers first. On Node 22.22.2 against a local test server, the authors observed on 2026-09-24 (a test, not a documented guarantee): a refused connection produced an `error` event and no `close` event within 8 s, the socket staying in `CONNECTING`; a connection dropped without a close frame produced `close` with code 1006 and `wasClean: false`, and no `error`; an invalid frame produced `error`, then `close` with code 1006; closing a socket that was still connecting produced two `error` events and no `close` within 0.3 s; and a close frame from the peer that was not followed by the end of the TCP connection produced no `close` event within 3 s, with `readyState` `CLOSING` and `send()` discarding its data without throwing, so such a socket is settled by its liveness timer.

The budgets are chosen to stay well below the only numeric connection-attempt limit located, a per-IP cap of about 150 connection attempts per rolling 10 minutes with a 10-minute ban beyond it [S, unverified on the live page]. The venue also limits simultaneous connections per client and rejects clients that reconnect too often, but neither threshold is published [S, U], so compliance with them is not established. Public REST calls are kept to one `AssetPairs` request at start and one `Time` request per 10 minutes (the venue's guidance for public endpoints is about one request per second [S]). The 15 s liveness timeout of §2 is stricter than the venue's official CLI (which pings every 30 s and treats 90 s of silence as a dead socket); with heartbeats about once per second [S] it costs nothing, and the owner's reading under decision condition C5 confirms that cadence before any capture. Liveness is per socket: a required channel that falls silent while other frames keep the socket live (trades or heartbeats while no book update arrives, for example) is not detected, and no rule cuts or refuses a segment for it; a quiet trade channel cannot be told from a quiet market [U]. In replay the policy's `maxBookAgeMs` stops quoting on a book older than its limit (§5.3), which bounds but does not remove the effect. This is disclosed, not a gate: it blocks neither PR-1 nor a capture. Every reconnect is a segment boundary.

Live checks the capture performs, on the same local book the normalizer builds (one shared adapter module holds the decode, book and checksum logic): the checksum of every book message (§8.2), the crossed-book check and the malformed-depth check of §5.3 (on a mismatch, a crossed book or a malformed update it records a `note` naming the condition, sends the `unsubscribe` above, then `subscribe`, so a fresh in-band snapshot follows; while a resync is already outstanding, or before the socket's first snapshot, it runs none of these three checks, Resync above), and the clock-step rule of §5.6 (recorded as a `note`; no resubscribe needed). A resubscribe never rewrites or withholds anything: the revealing frame is appended verbatim, the `unsubscribe` and `subscribe` records carry their own send clocks, and the normalizer makes the cut from the raw stream alone. The snapshot that follows the resubscribe starts the next segment (§5.3, reset rule).

### 8.2 Book messages and the checksum

Decode dispatches on `channel` first: `book` frames are book messages, `trade` frames are trade messages (§8.3), `instrument` and `status` frames are handled per §8.4, `heartbeat` is `ignore`, frames with `method` are method responses (§5.6). Parse by key, never by position.

```json
{"channel":"book","type":"snapshot","data":[{"symbol":"BTC/USD","bids":[{"price":62710.4,"qty":0.01000000}],"asks":[{"price":62710.5,"qty":0.93111634}],"checksum":1361442827}]}

```

(The `update` line is the venue's own test vector from `kraken-cli`; the snapshot line has the documented shape with illustrative values. A snapshot may or may not carry `timestamp`; the adapter treats it as optional and §5.3 never emits the snapshot.)

| adapter output | source |
|---|---|
| `kind` | `snapshot` when `type == "snapshot"`, `depth` when `type == "update"`; anything else is `malformed` |
| `checksum` | `checksum`, the lexeme of an unsigned 32-bit integer; absent is `malformed` |
| `venueTimeText`, `venueTime` (fixture `marketTime`) | `timestamp` (RFC 3339, microseconds) verbatim and floored to ms; absent on an `update` is `malformed` |
| `venueSeq` | `"ts:<timestamp>;crc:<checksum>"` |
| `bids`, `asks` | `data[0].bids`, `data[0].asks` as `[price lexeme, qty lexeme]` pairs; a `qty` lexeme equal to zero (`0`, `0.0`, `0.00000000`) deletes the level; an exponent lexeme in a level is `malformed` (§5.1) |

`data` may carry several elements; each is applied in array order as its own message (its own checksum verification and its own `book` event, distinguished by `elementIndex`); an element whose `symbol` is not the selected instrument's is `malformed` (R6, Instrument identity in §8.1).

**Checksum (the integrity gate), as implemented by the venue's official Go SDK (`api-go/pkg/book/checksum.go`, `L2Checksum`) and described in its Rust SDK guide (`kraken-api-sdk/rust/docs/guides/order-book.md`, "Checksum"):**

1. After applying the message (and truncating to the subscribed depth), take the top 10 asks from the lowest price upwards, then the top 10 bids from the highest price downwards (fewer if a side has fewer levels).
2. For each level, take the **wire lexeme** of the price, remove the decimal point, then strip all leading `0` characters; do the same with the wire lexeme of the quantity; append price then quantity. A level's lexemes are the ones from the message that last set that level (a snapshot or an update); this is why §5.1 keeps lexemes and never reformats. (Example values from the venue's guide as excerpted by search, unverified on the live page [S]: price `45285.2` -> `452852`; quantity `0.00100000` -> `100000`.)
3. Concatenate the ask string then the bid string and compute CRC32 (IEEE 802.3 polynomial, the `zlib`/`binascii` CRC-32, as an unsigned 32-bit integer). It must equal the message's `checksum`.

Test vectors. (1) The venue's documented worked example, pinned by the venue's official Rust SDK test `amendment_59_worked_example_matches_canon` (`kraken-api-sdk/rust/src/book/checksum_tests.rs`, lines 30 to 39, commit `a5d253c02036`): the 281-character concatenation `45285210000045286415457195345286615457110945289615456091145290215890660452918154553491452947445474945296135380000452975994554245299518772827452835100000004528341545820154528211000000045281010000000452803154592586452790799000045277633101034527753000000045277315460273745276615445238` has CRC32 `3310070434`; the same file pins the strip rules `45285.21000000 -> 4528521000000`, `0.00159953 -> 159953`, `0 -> ` (empty), `0.0 -> ` (empty), `0.000123 -> 123`. Recomputed on 2026-09-22 with Python `binascii.crc32`: `3310070434`. (2) A five-level vector computed by this contract's author with two independent CRC32 implementations (Node `zlib.crc32` and Python `binascii.crc32`), for a book holding asks `[62710.5 x 0.93111634, 62710.6 x 0.50000000, 62711.0 x 1.20000000]` and bids `[62710.4 x 0.01000000, 62709.1 x 2.00000000]`: the string is `62710593111634627106500000006271101200000006271041000000627091200000000` and the checksum is `1396696505`. The handoff's tests use both (A9); the `checksum` in the update frame above covers a fuller book than the two levels shown and is not reproducible from them.

Synchronization (contract §5.3 instantiated):

1. On a newly opened socket, book messages before its first `snapshot` are counted (`dropped.depthBeforeSnapshot`) and not applied; this is the only key for them, including after a `gap_disconnect`, except on an R9 socket, whose book items are counted only under `dropped.socketNotSubscribed` (§5.9). On the same socket, after a condition that invalidates the local book, whether or not it cut a segment (a failed snapshot verification, step 2; a checksum mismatch, step 3; a crossed book, step 4; or a malformed depth message, §5.3), and while a resync is outstanding (§8.1, Resync), every book message until the next `snapshot` is `dropped.depthWhileUnsynced`, also when it follows the resync's `subscribe` record. A clock cut (§5.6) keeps the verified book and drops no book message: the next verified update opens the new segment. A `snapshot_reset` (step 5) applies its snapshot at once. On each socket that R9 does not refuse, an update verified before the later of its three `success: true` acknowledgements and its instrument snapshot is applied and verified but emits nothing (`dropped.depthBeforeSubscribed`, §5.3).
2. A `snapshot` replaces the local book (both sides, truncated to the subscribed depth) and its checksum is verified. A snapshot that fails is no baseline: it opens no segment and uses no index, and it and the book messages until the next snapshot are `dropped.depthWhileUnsynced` (§5.3). No event is emitted.
3. An `update` is applied per §5.3, each side truncated to the subscribed depth, the checksum computed and compared. Equal: one `book` event is emitted, unless the socket's subscription gate (step 1) has not yet passed (`dropped.depthBeforeSubscribed`). Different: an open segment ends at the previous record (`checksum_mismatch`, §5.8); the update is not applied; everything until the next `snapshot` is `dropped.depthWhileUnsynced`.
4. A crossed local book after an applied update is `reconstruction_failure` (the update is not emitted; the segment ends at the previous record).
5. A `snapshot` while a segment is open is `snapshot_reset` (the segment ends at the previous record; the snapshot opens the next one).
6. The fixture emits the top `depth` (default 25) levels per side; `visibleSpanBps` is computed over emitted events.
7. A `snapshot` never followed by a verified `update` before the next `snapshot`, `ws_close` or end of capture is handled as §5.3 (First event) says: received after the socket's gate, it is a refused segment with no event (R6) whose `endReason` follows the precedence of §5.8; received before the gate, it yields no segment; on a socket R9 refuses, nothing yields a segment.
8. No sequence rule exists for this channel and none is applied; the checksum on every message is the only stream-position proof, and it is checked on every message (a documentation excerpt describes verification as optional [S]; this repository does not treat it as optional).

### 8.3 Trade messages

```json
{"channel":"trade","type":"update","data":[{"symbol":"BTC/USD","side":"buy","price":62710.5,"qty":0.00120000,"ord_type":"market","trade_id":81234567,"timestamp":"2026-07-09T17:20:01.130001Z"}]}
```

(Field names and types from the venue's official `kraken-cli` type `TradeData`, which carries `symbol` on every item [R `crates/kraken-core/src/subscribe/message/trade.rs:18-26`]; values illustrative.) One `trade` event per array element whose `symbol` is the selected instrument's, in array order; an element of another pair is `dropped.foreignSymbol` (R4) and never emitted. `marketTime = timestamp` floored to ms (`venueTimeText` keeps the string); `tradeId = trade_id` as a decimal string (`tradeIdOrdered: true`, §5.7); `aggressor = "buy"` when `side == "buy"`, `"sell"` when `side == "sell"` (the venue's official Rust SDK documents `side` as "Aggressor (taker) side of the print", `kraken-api-sdk` `rust/src/api/market/ws_types.rs:81-84,108-119`; the documentation page says "the side of the taker order" [S]), anything else `malformed`; `price`, `size` are the lexemes of `price`, `qty`; `venueSeq = "id:<trade_id>;ts:<timestamp>"`; `ordType` is kept in the normalize report's counts (`limit` and `market` taker orders; any other value is counted as `other` and never named, §5.10) and not in the fixture. A frame with `type == "snapshot"` is history (§5.4) and is not emitted. Several trades in one frame are several events with distinct `elementIndex` (§5.2); a search excerpt of the venue's documentation says that batching does not imply one taker order [S], so nothing is merged. Duplicates and regressions are keyed on `trade_id` per segment (§5.7).

### 8.4 Instrument and status frames

The `instrument` snapshot frame (`{"channel":"instrument","type":"snapshot","data":{"assets":[...],"pairs":[...]}}`) is the instrument specification. The adapter extracts the verbatim JSON text of the `pairs` element whose `symbol` is `BTC/USD` (`kind: 'instrument'`) and maps:

| `instrumentSpec` | source field | example (documentation, re-fetched at capture) |
|---|---|---|
| `venueSymbol` | `symbol` | `BTC/USD` |
| `tickSize` | `price_increment` (`tick_size` is deprecated by the venue and is only cross-checked when present) | `0.1` |
| `lotSize` | `qty_increment`, exponent lexemes converted exactly | `1e-08` -> `0.00000001` |
| `priceDecimals` / `qtyDecimals` / `costDecimals` | `price_precision` / `qty_precision` / `cost_precision` | 1 / 8 / 5 |
| `qtyMin` / `costMin` | `qty_min` / `cost_min` | `0.0001` / `0.5` |
| `status` | `status` (`online`, `cancel_only`, `post_only`, `limit_only`, `reduce_only`, `maintenance`, `work_in_progress`, `delisted`) | `online` |
| `aggressorSource`, `tradeStreamGranularity`, `tradeIdOrdered`, `integrity` | fixed by this adapter | `taker_side`, `per_fill`, `true`, `crc32_top10` |
| `source`, `fetchedAtIso` | the raw record reference and its receive time | |

Cross-check against the manifest's REST `AssetPairs` payload, which the capture requested for exactly this pair by its REST name (`XBTUSD`, the adapter's fixed mapping for `BTC/USD`; the REST response is keyed by the legacy code `XXBTZUSD` and carries `altname` `XBTUSD` and `wsname` `XBT/USD` [R `kraken-cli` `src/commands/schema.rs:1017-1045`, a unit test whose hand-written input is one `AssetPairs` `result` row in the raw wire shape; the CLI's code at `:378-422` rebuilds the key as `BTC/USD` from the row's `base` and `quote` and strips `altname`, `wsname`, `base`, `quote` and `lot`], which the capture's manifest records verbatim from the live response (the rule below compares only `altname`), as does the P0 listing when it is taken from REST `AssetPairs`; a P0 listing taken from the WebSocket `instrument` channel gives only `symbol`): the payload's `result` must hold exactly one entry whose `altname` equals the mapped name, and then `pair_decimals == price_precision`, `lot_decimals == qty_precision`, `tick_size == price_increment`; a disagreement, a missing pair in either source, or a pair `status` other than `online` at capture start is R5. The pair's status at capture start is its `status` in the capture's first instrument snapshot, on whichever socket it arrives (§8.1, Instrument identity); a REST `status`, when present, must also be `online`, and one that is absent is no disagreement, because the venue's official Rust SDK decodes it as optional and notes that Kraken omits it for many pairs [R `kraken-api-sdk` `rust/src/api/market/types.rs:430-431`, `rust/docs/guides/market-data.md:9`, which reports it omitted on about 13% of listed pairs in 2026-06]. Every later instrument frame is checked as Instrument identity in §8.1 says. A later `instrument` `update` frame that changes this pair's `status` is recorded in `venueStatus` (`source: "instrument"`) and reported; the fixture header keeps the start-of-capture specification.

`status` frames (§8.1) are `kind: 'status'`; every value other than `online` is listed in `capture.venueStatus` (`source: "status"`) with its raw record index.

### 8.5 Clocks and lag

`marketTime` for books is the update's `timestamp`, for trades the trade's `timestamp`; both are RFC 3339 strings with microsecond resolution floored to milliseconds (`provenance.timeBasis.marketTime` states this). No source read says which clock stamps them [U]; the lag statistics are computed per stream and the venue clock offset from method responses (`time_in`/`time_out`) per §5.6.

## 9. Versioning

- Raw capture format: `captureFormatVersion` (integer). Any change to record types or clock semantics increments it; additive optional fields do not (the unknown-property policy of §6); old raw files remain readable by keeping the old decoder.
- Fixture schema: `schemaVersion` 1 (synthetic, existing) and 2 (this document). Additive optional fields do not bump the version (the unknown-property policy of §6); a change to the meaning of `obsTime`, `marketTime`, `seq` or the header requirements does.
- Engine fixed-point scales: a change to `PRICE_SCALE`, `QTY_SCALE` or `MONEY_SCALE` is a versioned engine change (handoff §0): it changes the width of decimal strings in ledgers and results, so it bumps `LEDGER_SCHEMA_VERSION`, updates LEDGER_SCHEMA.md, ACCOUNTING.md and EVENT_SCHEMA.md, and is recorded in every fixture header's `qtyScale`/`priceScale`. Committed version-1 fixtures stay byte-identical; the loader rescales exactly, and `toWire`/`fixtureContentHash` format sizes at the fixture header's declared `qtyScale`, so version-1 content hashes do not change.
- Adapter: `adapter.version` in the header; a change to any field mapping or synchronization rule bumps it, and re-normalization of existing raw files is expected to change fixture hashes (recorded in the normalize report).
- Ledger schema is unchanged by the capture/normalize PR (version 1); only the precision migration bumps it.
- Normalize report: `reportFormatVersion` (integer, §5.10). The report's schema is closed, so any new field is a version change.
- JSON Schemas: a change to `schemas/capture-record.v1.schema.json`, `schemas/fixture.v2.schema.json` or `schemas/normalize-report.v1.schema.json` updates `schemas/examples/` and `tests/schemas.test.ts` in the same change, so every record type, header, event and report keeps a valid example and each new rule gets a derived failure case.
